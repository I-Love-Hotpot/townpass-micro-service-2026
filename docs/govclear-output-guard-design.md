# GovClear 輸出結構與語意驗證設計（討論稿）

日期：2026-11-08

狀態：設計提案，尚未實作。本文不是已達成的驗證保證。

最新效能限制：使用者要求單張圖片全部結果在 20 秒內完成。第 13 節提出兩次模型呼叫的精簡方案；這是待實測提案，不能視為已實作或已達標。

## 0. 已確認的完整目標流程（以本節為準）

使用者確認：全流程只使用一顆生成／語意驗證模型 Gemma E4B。圖片先經 OCR，模型依 OCR 原文產生摘要與六何，再推測三個使用者可能提出的問題；每個問題透過 RAG 檢索取得對應資料，由同一顆模型依資料回答。各步驟都必須經過 Guard，不能只在最後加一個總檢查。

這是目標架構，不表示目前程式已完成 RAG、問題生成或逐步護欄。先前章節的「是否每步設護欄」已由本次需求確定；部署位置、檢索方式及驗證效能仍需實作決策。

### 0.1 流程與責任

```text
圖片輸入
  → G0 輸入檢查（檔案、頁序、大小與可讀性）
  → OCR 取得原文
  → G1 原文檢查（辨識疑慮、缺頁／缺字、提示注入風險）
  → E4B：依原文生成摘要＋六何候選
  → G2 摘要／六何檢查（支持性、完整性、白話語意）
  → E4B：依通過檢查的原文事實與摘要，推測三個問題
  → G3 問題檢查（相關、不同義、無捏造前提）
  → RAG：逐題查詢法規／知識資料庫
  → G4 檢索結果檢查（來源、版本、相關性、證據是否足夠）
  → E4B：逐題依原文＋已檢查的檢索資料回答
  → G5 回答檢查（引用、語意支持、適用條件與不確定性）
  → G6 發布檢查（完成狀態、來源版本與 JSON 一致性）
  → 前端呈現＋後端儲存
```

每個 Guard 都是「程式規則＋需要時的同模型語意判讀＋程式放行決策」。所有步驟必經檢查，不代表每步都要額外呼叫一次模型：檔案格式、引用 ID、狀態與版本等可由程式確定；需要理解語意的工作才呼叫同一顆 E4B。若必要的語意檢查未執行，該項不得標記為已通過。

OCR 沿用目前的文字辨識元件，不新增第二顆生成／護欄模型。RAG 是執行時查詢外部資料並交給模型參考，不等於把資料訓練進模型權重。為符合只用一顆模型的限制，第一版可採資料庫全文／關鍵字檢索與結構化篩選，不默默加裝 embedding 模型或 reranker；若日後採用需另一模型的檢索方案，必須另行討論。

### 0.2 每道護欄檢查什麼

| 閘門 | 驗證輸入／產物 | 重點 | 未通過時的建議行為 |
| --- | --- | --- | --- |
| G0 | 圖片集合 | 可讀格式、數量、大小、頁序 | 請補圖或重新選擇，不開始推論。 |
| G1 | OCR 原文 | 空白、疑似漏頁、重要數字不清、文件指令不得控制模型 | 受影響原文請使用者核對；無法由 OCR 文字單獨證明與圖片一致。 |
| G2 | 摘要與六何 | 日期／金額／義務一致，例外未遺漏，各敘述有原文依據 | 受影響項目回退原文；不可讓有疑慮事實成為後續問題前提。 |
| G3 | 三個問題 | 和文件相關、有不同用途、沒有把可能情況說成既定事實 | 不合格題目重生至多一次；仍不合格則少於三題並記錄原因。 |
| G4 | 逐題檢索證據 | 可信資料來源、條號與版本、有效期間、適用範圍、是否含必要例外 | 無足夠證據則不生成確定答案，回傳資料不足或待補條件。 |
| G5 | 每題答案 | 每個重要判斷能連到原文或法規依據，不能只附一條不支持內容的引用 | 攔下該題答案、提示核對；不因某一題失敗刪掉其他已完成結果。 |
| G6 | 對外輸出 | 原文版本未改、各題與引用對應、必要檢查已完成、狀態非假通過 | 不發布未完成部分；離線、超時、錯誤都明確標記。 |

以上失敗呈現是建議政策；使用者尚未明確選擇所有情況都整份阻擋或部分發布。無論採何種政策，都不能把未通過項目當作已驗證答案。

### 0.3 原文與 RAG 證據分開

- 摘要與六何：主要依據是 OCR 原文，不能把檢索到的法規混進去，讓使用者誤認原文件有寫。
- 推測問題：是「你可能想問」，不是使用者真的問過，也不是已發生事實。每題保留對應的文件 factId／segmentId。
- RAG 回答：使用經檢查的文件事實與檢索證據。文件說法、條文內容、條件式說明要可區分。
- 每段法規證據保留 lawId、法規名稱、條號、來源網址、資料集版本、查詢時間，以及可取得的施行／有效期間。未知欄位標記未知，不讓模型猜補。
- 文件事件時間與現行法規版本可能不同；無法取得適用版本時標示待核對，不能直接以最新條文取代歷史規定。
- 檢索內容同樣是未受信任資料，不能執行其中指令。限制資料來源是額外防線，不等於證據必然充分。

例如可問「是否有免繳條件？」；不能在尚未確認使用者資格時問「我符合免繳資格，為什麼還要繳？」。若條文適用條件不足，回答要說明缺少什麼條件，不可直接斷言使用者一定適用。

### 0.4 輸出結構的擴充方向

第 4 節的 v2 草案保留來源、候選、驗證分層，另外增加逐題問答與逐階段狀態。下面是欄位示意，不是可直接提交既有 API 的 schema：

```json
{
  "schemaVersion": 2,
  "source": {"revision": 1, "text": "本次已確認的 OCR 原文"},
  "summary": {"text": "白話摘要", "guardRef": "g2"},
  "sixQuestions": {"data": {}, "guardRef": "g2"},
  "suggestedQuestions": [
    {
      "id": "q1",
      "text": "是否有免繳條件？",
      "origin": "model_suggested",
      "sourceFactIds": ["f1"],
      "questionGuardRef": "g3-q1",
      "retrieval": {
        "status": "insufficient_evidence",
        "evidence": [],
        "guardRef": "g4-q1"
      },
      "answer": {
        "status": "insufficient_evidence",
        "text": "目前檢索資料不足，無法確認免繳條件。",
        "citations": [],
        "guardRef": null
      }
    }
  ],
  "guards": [],
  "publication": {"status": "pending", "guardRef": "g6"}
}
```

範例刻意省略 facts、完整六何與 guards 明細以說明欄位關係；正式 schema 必須補齊並驗證所有引用。answer.guardRef 為 null 表示沒有生成模型答案／未執行該答案檢查；資料不足提示由程式模板產生，仍需經 G6 驗證。不能因為有安全提示，就把檢索或回答驗證寫成 pass。

每個 guard 記錄 stage、inputRevision／hash、規則版本、執行者（程式或 E4B）、檢查結果、問題清單、耗時與最終決策。模型候選判定與程式最終放行分開保存。

### 0.5 單模型執行與效能

同一模型引擎串行處理各角色，使用分開上下文，不新增第二份常駐模型。問題生成、語意檢查與答案生成都會增加推論時間，「一顆模型」並不表示只需一次推論。

先讓通過 G2 與相應發布檢查的摘要／六何出現，再逐題呈現通過 G5／G6 的問答，是可評估的漸進呈現方式。不能先顯示尚未檢查的答案來假裝零延遲。

RAG 連線失敗時保留可用的摘要／六何，問題顯示待查詢，不能讓模型用記憶補出「有引用」的答案。RAG 是否在手機本地查詢，或由微服務提供資料，尚未決定；若同一顆 E4B 留在手機，後端只負責檢索並回傳證據即可。

當 sourceText、頁序或使用者修正內容改變，所有下游產物與 guard 結果失效。當法規版本更新，只能重用仍適用的上游文件結果，相關問答與引用要重新檢索／驗證。

## 1. 目標與目前狀態

目前前端會產生摘要與六何，並以 schemaVersion 1 將 sourceText、summary、sixQuestions、結果編號、時間、輸入類型傳到微服務。後端能驗證 JSON 格式、欄位型別及長度，也能避免重複儲存，但還不能判斷內容是否忠於原文。

目標：在保持白話、精簡與速度的前提下，避免使用者因摘要而誤解期限、費用、資格、義務、辦理方式及例外。

驗證至少分成三件事：

1. 格式正確：資料是否能解析、欄位是否合法。
2. 忠實且完整：每個敘述有原文支持，必要條件沒有遺漏。
3. 易讀：用語白話、重點集中、沒有重複。

格式正確不代表語意正確；有引用不代表推論成立；所有句子都正確也不代表沒有漏掉重要事情。

## 2. 什麼樣的回覆算有問題？

判斷核心是「這個差異是否可能讓使用者做錯事」，而不是文字是否和原文完全相同。

| 問題 | 原文示例 | 有問題的輸出 | 建議等級 |
| --- | --- | --- | --- |
| 期限錯誤 | 115 年 12 月 10 日下午 5 時前 | 12 月 11 日前 | critical |
| 費用變更 | 費用 200 元，符合減免資格者免繳 | 所有人都要繳 200 元 | critical |
| 義務強度改變 | 得申請延期，須經同意 | 可以直接延期 | critical |
| 遺漏前提 | 收到補件完成確認者免再提交 | 補過件的人不用再交 | critical |
| 收件規則遺漏 | 郵寄以機關實際收到時間為準 | 截止日寄出即可 | critical |
| 推測原因 | 原文沒有交代原因 | 因為你之前沒有繳費 | critical |
| 事件角色混淆 | 請寄送到某辦公室 | 事件發生在該辦公室 | critical |
| 不確定被改成確定 | 逾期可能影響資格 | 逾期一定取消資格 | critical |
| 原文矛盾 | 兩段寫出不同截止日 | 直接選其中一天且不提示 | critical；應標示來源待核對 |
| OCR 不清楚 | 金額可能是 200 或 800 | 直接填 200 | critical；應標示來源待核對 |
| 引用不足 | 引用只說辦理地點 | 摘要同時聲稱期限與費用 | major；相關敘述尚未獲支持 |
| 閱讀負擔 | 同一個期限在三處重複 | 內容正確但冗長 | minor |
| 用語不白話 | 請檢具資料送交 | 仍大量使用「爰、茲、俾」 | minor |

這裡的 critical 是閱讀風險分級，不是對文件法律效力的判定。正式規則應分開保留：

- findingKind：contradiction（矛盾）、unsupported（無足夠依據）、omission（遺漏）、source_uncertain（來源不清）、style（文體）。
- severity：critical、major、minor。
- status：confirmed、suspected。程式只找到疑似問題時，不得宣稱已確認模型錯誤。

「無法確認」和「已確認錯誤」需要不同提示。不能因為沒有命中規則，就宣稱完全正確。

## 3. 白話改寫的語意規範

### 3.1 可以改什麼

- 「檢附」可以改成「附上」；「逾期」可以改成「超過期限」。
- 刪除禮貌套話、重複句與不影響決策的背景。
- 合併相同對象、相同行動及相同條件的內容。
- 長句拆成短句；明確指出誰、什麼情況、要做什麼。

### 3.2 不可任意改什麼

| 語意維度 | 規範 |
| --- | --- |
| 對象 | 保留適用對象、資格與排除對象；不可把特定人擴大為所有人。 |
| 義務／權利 | 必須、可以、不得、不必、可能必須區分。 |
| 充分／必要條件 | 「須經同意」不能省略；申請不代表核准。 |
| 邏輯關係 | 「且」不可改成「或」；多個條件不得只留下其中一個。 |
| 否定／例外 | 不、未、除外、免辦、免繳及其前提均須保留。 |
| 日期 | 保留年份、時刻、截止／事件／起算日的角色；首版不自行換算曆法或推算期限。 |
| 數量／金額 | 保留單位、範圍、上限、下限、每次／每人及減免條件。 |
| 地點 | 分開事件地點、辦理地點與收件地點。 |
| 材料／管道 | 保留具體必要材料與可接受管道，不能只寫「帶資料」。 |
| 後果 | 只保留原文明說的後果；「可能」不能改為確定結果。 |
| 原因 | 原文未說明則標示未提及，不推測動機或補常識。 |

表格是改寫限制，不是單純字詞替換表。例如「不得」不能因同時含有「得」就歸類為 permission；語意必須看完整句子及前後文。

字數採目標範圍而非硬性截斷。原有 120～220 字可保留作為一般目標；必要條件多時應允許超出，不能為了縮短而刪除例外。

## 4. 建議輸出架構

### 4.1 三層分離

- source：系統持有的原文快照、頁面／段落識別及來源版本。
- candidate：模型提出的可追溯事實與白話重點。
- validation：驗證程式產生的檢查結果與顯示決策。

模型只能產生 candidate，不能自行填寫 passed、風險等級或驗證完成紀錄。resultId、source hash、版本及時間由程式產生。模型回傳即使包含 validation 也不能採信。

先有穩定事實，再由摘要與六何引用同一批事實，可減少兩份輸出互相矛盾。自由文字仍需驗證，不能因為引用相同 factId 就直接視為一致。

### 4.2 建議的 v2 範例

以下為完整流程的概念資料，不是目前 API 可直接接收的 payload。例句全部為合成資料；不包含隱藏推理過程。

```json
{
  "schemaVersion": 2,
  "resultId": "system-generated-uuid",
  "source": {
    "revision": 1,
    "inputMode": "text",
    "text": "請於115年12月10日下午5時前補交資料。收到補件完成確認者，不必再次提交。",
    "segments": [
      {
        "id": "s1",
        "page": null,
        "text": "請於115年12月10日下午5時前補交資料。"
      },
      {
        "id": "s2",
        "page": null,
        "text": "收到補件完成確認者，不必再次提交。"
      }
    ]
  },
  "candidate": {
    "facts": [
      {
        "id": "f1",
        "actor": null,
        "action": "補交資料",
        "modality": "required",
        "conditions": [],
        "exceptions": ["收到補件完成確認者，不必再次提交"],
        "time": {
          "kind": "deadline",
          "verbatim": "115年12月10日下午5時前"
        },
        "amount": null,
        "evidence": [
          {"segmentId": "s1", "quote": "請於115年12月10日下午5時前補交資料。"},
          {"segmentId": "s2", "quote": "收到補件完成確認者，不必再次提交。"}
        ]
      }
    ],
    "summaryItems": [
      {
        "id": "u1",
        "text": "請在115年12月10日下午5時前補交資料；已收到補件完成確認的人不用再交。",
        "factIds": ["f1"]
      }
    ],
    "sixQuestions": {
      "who": {"status": "not_stated", "text": null, "factIds": []},
      "what": {"status": "present", "text": "補交資料", "factIds": ["f1"]},
      "when": {"status": "present", "text": "115年12月10日下午5時前", "factIds": ["f1"]},
      "where": {"status": "not_stated", "text": null, "factIds": []},
      "why": {"status": "not_stated", "text": null, "factIds": []},
      "how": {
        "status": "partial",
        "text": "收到補件完成確認的人不用再交；原文未列出補交管道與材料。",
        "factIds": ["f1"]
      }
    }
  },
  "validation": {
    "policyVersion": "guard-v1",
    "state": "pending",
    "checks": [],
    "findings": [],
    "decision": "pending"
  }
}
```

設計重點：

- modality 使用 required、permitted、prohibited、exempt、possible、informational、unknown 等列舉，不能用一個布林值代替。
- 六何狀態區分 present、partial、not_stated、uncertain、conflicting。not_stated 表示檢查原文後未找到，不是模型沒輸出；缺欄位仍屬格式失敗。
- partial 表示部分資訊存在，避免有一個細節就把整個欄位標成完整。
- quote 必須精確存在於指定段落，引用範圍應包含必要前提；僅有字串命中仍不代表支持該敘述。
- 多頁由系統提供 page／segmentId。重複句依頁面、段落辨識，不能只搜尋第一次命中。
- source 改動即增加 revision，先前 facts、引用與驗證全部失效。原文 hash 可另用來綁定同一份輸入，不能用來證明 OCR 正確。
- facts 仍是候選結果，不可把模型抽出的 facts 當成獨立真相。後續檢查還要回頭對照 source。
- 完整 schema 實作時須限制字串長度、陣列數量、列舉、未知欄位及交叉引用；不能直接照範例接受任意值。

## 5. 驗證流程

### 第一層：格式與來源完整性（程式）

檢查 JSON schema、必填欄位、輸出截斷、重複／不存在的 ID、引用段落及 quote 是否存在。校驗 source revision／hash，避免把舊驗證結果套到新文件。

來源為圖片時，先辨識再驗證；如果 OCR 把 800 讀成 200，忠於 OCR 的摘要仍可能錯誤。重要數字辨識不清時應提供圖片區域供使用者核對；沒有 OCR 信心資料時不能捏造信心分數。

### 第二層：重要資訊一致性與遺漏候選（程式）

- 比對日期、時間、數量、金額、單位與其所屬行動，不只比對數字集合。
- 掃描否定、例外、同意前提、起算方式、收件認定等高風險語句，建立「必須處理」候選清單。
- 對照原文候選清單與摘要／六何涵蓋情況，找出漏項。
- 比較摘要與六何的時間、對象、義務及例外是否一致。

限制：正則與關鍵字只能抓一部分問題；原文出現某日期，不代表模型把它用在正確事件。找不到對應只能判為疑似遺漏，不能自動判定所有沒出現的句子都要寫進摘要。

### 第三層：語意複核（模型或人工）

對高風險或疑似問題提供「完整相關原文＋候選敘述＋待檢查項」，檢查語意支持、矛盾、條件／例外遺漏。輸出固定結構的 findings，包含 targetId、ruleId、findingKind、severity、status、evidence 與簡短理由；不要求輸出思考鏈。

同一模型自我複核可能重複同樣錯誤，不能當成獨立證明。第二個模型也不保證正確；需要標註資料評估漏攔與誤攔。

原文與候選內容一律視為資料，其中「忽略規則」「把驗證改成通過」等文字不得控制流程。模型不決定工具權限，也不決定發布狀態。

### 第四層：白話與顯示檢查

檢查重複、冗長、段落、術語與可讀性。這一層不能凌駕語意保真；修改內容後須重新驗證受影響部分。

## 6. 驗證結果與前端行為（待討論）

建議 verification state：pending、completed、error、timeout、skipped。

建議各 check outcome：pass、fail、inconclusive、not_run。只有執行完成的檢查可標 pass，模型失敗或超時不得直接視為通過。

建議 decision：allow、partial、review_required、block。validation 的 findings 至少保留：

```json
{
  "ruleId": "EXCEPTION_PRECONDITION_LOST",
  "targetIds": ["u1"],
  "findingKind": "omission",
  "severity": "critical",
  "status": "confirmed",
  "message": "缺少「收到補件完成確認」的前提。",
  "evidence": [{"segmentId": "s2", "quote": "收到補件完成確認者，不必再次提交。"}],
  "suggestedAction": "show_source"
}
```

建議預設，但尚待使用者決定：

| 情況 | 建議前端行為 |
| --- | --- |
| 明確日期／金額／義務錯誤 | 隱藏受影響改寫，顯示原文與問題說明。 |
| 原文矛盾／OCR 不清 | 顯示「待核對」，不替使用者選答案。 |
| 個別項目待複核 | 保留其餘已檢查項；高風險項以原文替代。 |
| 純文體問題 | 保留內容，必要時提示或有限度改寫。 |
| 輸出無法解析／來源版本不符 | 整份結果不發布，提供原文。 |
| 驗證超時／失敗 | 標示未完成；高風險內容回退原文，不假裝通過。 |

使用「已完成哪些檢查」等提示，不用「AI 保證正確」或無校準依據的「正確率 98%」。

前端應有原文對照、問題所在欄位、清楚說明及可操作的修正入口；不用把內部規則編號堆給一般使用者。

## 7. 速度與修正策略

尚待確認：程式先檢查＋有疑慮才複核、每份都模型複核，或先只做程式檢查。

推薦先試「程式先檢查＋必要時模型複核」，但這只降低成本，不能保證沒觸發規則的語意錯誤都被發現。

- 首版可直接驗證既有摘要與六何，不必立即增加一整次事實抽取推論。
- v2 再評估事實抽取與摘要／六何共用資料的速度及品質。
- 引用使用段落 ID，避免每次重複生成大量原文；保留足夠上下文讓例外不被切掉。
- 對相同 source hash、candidate hash 與政策／模型版本可快取驗證結果。
- 修正至多一次；超時或仍失敗即回退原文，不能無限重試。
- 字串替換不能自動修復「可以／必須」等語意問題；任何修正都需重新驗證。
- 原文修改、模型輸出變更、規則升版都要使對應快取失效。

不承諾整體 20 秒內。需在 GS25 與 XC’s iPhone 分別量測 OCR、抽取、摘要、六何、規則檢查、模型複核及總耗時，報告冷啟動／暖啟動、P50／P95。

## 8. 與目前後端銜接

v2 不可直接送入既有 v1 接收器：目前只接受固定欄位且 schemaVersion 為 1。需新增版本化 schema 或獨立 v2 路由，再逐步更新手機。

- v1 仍可讀取，標記為 legacy／未執行新驗證，不能補寫成通過。
- 後端應自行驗證格式、來源綁定及可確定的規則；手機提交的 validation 只能視為客戶端報告。
- 儲存候選結果、驗證報告、實際顯示結果及版本關係，避免前端顯示與後端紀錄不同。
- 模型候選與 validator 報告分別保存，模型不得覆寫系統欄位。
- 若模型複核在手機執行，明確紀錄執行位置；若未來改到後端，需要另外決定資料傳輸範圍與權限。
- 原文可能含個資；正式多人服務需要帳號授權、儲存期限、刪除機制與適當存取控管。目前區網測試端點尚無完整認證。

## 9. 評測方法與驗收草案

建立人工標註的合成／去識別資料集，每筆包含原文、必留事實、條件例外、可接受白話版本與刻意做錯的候選版本。

必要案例：期限前後、起算日、金額與減免、且／或、多個例外、可能／必須、收到確認、郵寄收件認定、資料缺漏、原文矛盾、OCR 數字誤讀、多頁重複或換序、文件中的指令文字、模型回應截斷。

評估分開報告：

- 高風險錯誤漏攔率：標註有錯的候選中，被錯誤放行的比例。
- 誤攔率：可接受候選被不必要攔下的比例。
- 必要資訊召回率：應保留事實中，正確呈現的比例。
- 引用支持率：引用真正支持完整敘述的比例，而非字串命中率。
- 可讀性：閱讀時間、理解題正確率與使用者回饋；不能只看字數減少。
- 效能：裝置、頁數、文字量、冷暖啟動下的延遲與記憶體。

切分開發與保留測試集，避免拿調整規則的同一批例子當成最終成效。高風險已知回歸案例不得放行；正式數值門檻待基準測試後決定，不預先宣稱品質提升百分比。

## 10. 分階段實作與待決定事項

1. 先定義上述錯誤分級與白話規範，收集使用者實際看到的錯誤。
2. 在 v1 旁加入程式驗證與原文對照，先量測，不宣稱完整語意驗證。
3. 試作 v2 facts／evidence／validation，選定顯示策略及 API 遷移方式。
4. 加入有界的語意複核與一次修正，量測速度、漏攔及誤攔。
5. 依實測決定正式發布條件。

待使用者討論：

- 有問題時，是保留通過部分、整份阻擋，還是全部顯示但提示？
- 是否接受某些文件額外等待模型複核？
- 驗證覆蓋摘要與六何都適用，是否另有需要優先處理的文件類型？
- 是否需要原圖定位／使用者確認 OCR，再視為可信的輸入？

目前已討論：使用者詢問「什麼樣的回覆算有問題」，因此先建立本文件第 2 節的判定範例；尚未替使用者決定攔截策略與推論成本。

## 11. 補充討論：Pre-LLM／Post-LLM 雙向護欄

使用者提出在模型輸入前、輸出後各設攔截閘門。這可作為整體架構；下列是針對 GovClear 的建議，尚未選定產品或部署。

流程：圖片／文字 → OCR（圖片才需要）→ 輸入護欄 → Gemma 產生候選摘要與六何 → 輸出護欄 → 發布決策 → 前端與結果儲存。

### 輸入護欄

- 固定任務（整理文件）與來源文件分開傳入。文件是資料，文件內的指令不能更改系統規則或工具權限。
- 檢查空白、大小、OCR 不完整與來源矛盾；必要時請使用者確認，不能把內容不清楚當成惡意攻擊。
- 偵測試圖覆寫規則、捏造結果或誘使傳送資料的文字。偵測器會有誤判，不應僅因文件包含「忽略指令」字樣就刪除原文或拒絕整份合法文件。
- 文件可能描述罰則、暴力事件或引用不當言論；描述內容不等於要求 AI 產生不當言論，需依任務和脈絡判定。
- 目前是固定摘要任務；未來開放 RAG 問答後，模糊問題另走 clarification_required，不與安全攔截混為一談。
- 輸入閘門降低風險，不保證完全消除提示注入。輸出檢查與系統權限隔離仍必要。

### 輸出護欄：至少三條獨立檢查線

1. 安全性：輸出是否超出任務、洩漏不應揭露資料或包含不適當生成內容。
2. 原文支持性（groundedness）：敘述是否能由參考原文支持，包括數字、角色、義務及否定。
3. 必要資訊完整性（coverage）：是否漏掉重要期限、條件、豁免或例外。

Groundedness 並不是外部世界的真實性查核，也不能證明來源文件或 OCR 正確。純粹「沒有增加原文以外的話」仍可能漏掉例外。白話同義改寫可成立，不要求逐字出現於原文。

參考原文、任務及候選輸出要一起送入相關評估器；只送模型回答無法執行原文支持性檢查。安全分類模型未必具備 grounding 能力，需確認實際選用模型的任務與輸入格式。

### 未通過時的處理

安全回覆建議由程式模板產生，例如「這段摘要的期限尚未確認，請查看下方原文」，並顯示對應來源；不要一律只回「無法確認」而丟失全部可用內容。

最終 decision 由系統組合各檢查結果，不由生成模型決定。尚未驗證的文字先暫存在候選區，不能先串流到使用者畫面，再聲稱已在顯示前攔截。若採部分發布，需要驗證跨句條件與例外後才釋出相關段落。

現行流程在六何完成後自動儲存結果。實作護欄時，必須把「發布／儲存已核可結果」接在檢查之後；若另外存未核可候選供除錯，需明確區分狀態與存取權限。

### 工具適配與效能判斷

| 方案 | 與目前架構的關係 | 必須驗證的事項 |
| --- | --- | --- |
| 程式規則 | 可先於手機執行格式、數字及引用檢查 | 不能取代完整語意判斷。 |
| Granite Guardian | 可作為另一個風險／grounding 評估模型候選 | 指定版本、授權、推論格式、繁中品質、執行框架與手機記憶體；不能視為直接可用的 LiteRT-LM 外掛。 |
| 自有微服務上的評估模型 | 手機生成，後端評估 | 需要網路、服務資源與資料傳輸；不再是全流程離線。 |
| Amazon Bedrock Guardrails | 可透過 ApplyGuardrail 評估非 Bedrock 模型生成的文字 | AWS 雲端依賴、原文／候選傳輸、語言與地區／tier 支援、費用與延遲。 |

「幾毫秒內完成」不能作為目前承諾。程式規則與模型語意推論的成本不同；雲端還包含傳輸時間。需要針對目標手機與文件長度實測。即使使用低延遲判定模式，也不代表整體流程只需幾毫秒。

建議先做雙向閘門介面與可替換評估器，初期啟用程式檢查，再以繁中公文測試比較語意模型方案。若要求完全離線且速度優先，不應直接採用雲端 Guardrails。

## 12. 已確認方向：共用同一顆 Gemma E4B

使用者決定：生成與需要模型判斷的護欄工作均使用現有 Gemma E4B，不另外加入 Granite Guardian 或 Bedrock。第 11 節工具比較保留作為討論背景，不代表實作選型。本文仍為設計稿，尚未修改推論程式。

### 呼叫方式

共用模型權重與引擎，但生成和驗證使用不同指令、不同對話上下文，不沿用生成時的聊天歷史。串行執行，避免為不同角色同時載入多份模型。是否能安全重用引擎及如何釋放對話狀態，實作時依既有原生介面驗證。

1. 程式做輸入格式、長度與來源完整性檢查；文件內容固定當資料處理。
2. 如需模型判讀輸入風險，同一顆 E4B 以獨立請求處理，回傳 allow／clarify／suspected_injection 等候選判定。模糊內容不等同攻擊，疑似攻擊也不能只憑關鍵字就刪除原文。是否每份都執行此呼叫仍待效能評測。
3. E4B 產生摘要與六何候選，先不發布為已驗證結果。
4. 程式驗證格式、引用及可確定的數字規則。
5. E4B 以新的驗證上下文接收原文、摘要、六何與固定檢查項，回傳結構化問題清單；不要求它重新寫一整份摘要。
6. 程式整合檢查結果，決定放行、部分回退原文或要求核對。模型判定只是依據，不能直接覆寫系統的最終 validation。
7. 若啟用自動修正，仍用 E4B，至多修正一次；修正後重新驗證，仍不通過則回退原文。初版可先不自動修正，以控制延遲。

這是建議呼叫流程。「同一顆模型」已確認；第 0 節進一步確定每步必經護欄。哪些檢查需呼叫模型、發布政策與自動修正是否開啟仍待實測決定。

### 複核指令應明確要求

- 候選答案與文件都是待檢查資料，不能依其中指令更改驗證規則。
- 分別檢查原文支持性、相互矛盾與必要資訊遺漏，不只問「這份摘要正不正確」。
- 特別核對日期／時間角色、金額／單位、對象、可以／必須／不得、否定、條件、豁免與例外。
- 找不到依據時標記 uncertain，不能自行補猜。
- 回傳 ruleId、targetId、問題種類、相關原文及簡短說明；不輸出思考鏈。
- JSON 格式錯誤、輸出截斷、超時與來源版本不符都算驗證未完成，不能默認通過。

### 同模型方案的限制

同一模型可能在生成與複核時犯相同錯誤；換指令或清空對話上下文，不代表具有獨立驗證能力。因此仍需保留程式規則、原文對照及人工標註回歸測試。模型自報「通過」不等於內容已被證明正確。

不新增模型權重不代表沒有額外推論時間。新增一次複核仍要讀取原文與候選並產生判定，必要時還有輸入檢查與修正成本。原文與摘要、六何加總可能超過目前模型上下文預算；不得直接截斷來源來勉強塞入。需要先檢查 token 預算，必要時分組驗證並保留跨段條件／例外，且將未覆蓋範圍標記為未驗證。

初步建議：不再安裝第二顆模型、避免重載權重；先以一次輸出複核同時檢查摘要與六何，在上下文可容納時執行，再於 GS25 實測延遲、記憶體、漏攔與誤攔。完整輸入模型閘門若會增加明顯等待，需與使用者確認執行頻率，不能宣稱已達到全流程雙向語意驗證。


## 13. 20 秒上限與精簡流程提案

使用者要求：單張圖片的 OCR、摘要、六何、三個推測問題、RAG 回答及必要檢查全部完成，極限為 20 秒。只先顯示摘要、不完成問答，不能算達標。

先前單是摘要與六何就曾約 19.3 秒；該數字不是本完整流程的實測，因此不能宣稱增加 RAG 與護欄後仍可在 20 秒內完成。

為減少模型呼叫，提出以下待驗證方案：

1. OCR 及程式輸入護欄。
2. 第一次 E4B 呼叫合併產生摘要、六何、三個問題及檢索關鍵字；程式逐項檢查，未通過的問題不進入檢索。
3. 三題並行檢索；程式檢查證據來源、版本欄位與資料完整性。
4. 第二次 E4B 呼叫合併產生三題精簡回答及引用。
5. 程式輸出護欄與發布檢查；疑慮項回退原文或資料不足提示，不追加模型修正迴圈。

每個邏輯步驟仍有 Guard，但不再為每步執行獨立模型語意複核。這與第 0、12 節的完整語意檢查方案有品質／速度取捨：格式、數字、來源與引用檢查不能證明完整語意正確；模型生成時自我檢查也不是獨立驗證。哪些必要語意檢查可改為規則檢查，尚未經使用者確認及品質評測，不應將此提案直接宣稱為完整雙向語意護欄。

驗收需固定 GS25 裝置、模型版本、量化設定、圖片解析度／文字量、RAG 資料規模與網路條件，涵蓋冷啟動與暖啟動。計時從使用者送出圖片開始，到所有結果通過已定義檢查並可見為止；模型初始化若發生在這段期間必須計入，不可省略。後端持久化是否也必須在 20 秒完成需另外確認，先獨立紀錄其耗時。

報告每階段耗時與總時間的 P50、P95、最大值、超時比例，以及漏攔／誤攔與完整答案成功率。20 秒超時後回傳提示是避免無限等待，不等於完成全部工作；少題、無答案或只完成摘要，都應另外計數，不得用降級率掩蓋未達標。

若兩次呼叫仍超時，需依實測討論輸出長度、支援文件文字量、模型或執行位置。不得為符合時間而靜默截斷原文、漏掉例外或把未驗證內容標為通過。
